# Java MCP 2026-07-28 implementation plan

**Goal:** Deliver an independent Spring Boot module implementing MCP 2026-07-28, verified against the official TypeScript SDK and the normative specification.
**Why planning is required:** Explicit user request; reusable public API, protocol, security and cross-runtime compatibility contracts.
**Current authorization:** Implement the specification locally (user: “implementiamo lo spec”, 2026-10-14). No GitHub repository, remote publication or product migration.
**Current stage:** Local HTTP/tools implementation complete and verified on 2026-10-14. Outcomes 0–7 have passed their local gates; public distribution, product adoption and optional capabilities remain separate work. Evidence and limitations: [docs/compatibility.md](../../../docs/compatibility.md).
**First-release profile:** HTTP/tools, as discussed before this request. Capability expansion is a material scope change and must update this plan and the normative test inventory.

## Acceptance

- Bootstrap: a reproducible devenv, pinned JVM/npm dependencies, working Gradle wrapper, library/sample builds, and an explicit distinction between bootstrap checks and MCP conformance.
- Implementation: all scenarios in the agreed protocol profile pass against the pinned reference and Java endpoint; each normative requirement has a named test.
- Spring integration: auto-configuration backs off for consumer beans, disabled configuration exposes no route, metadata is generated, library artifacts are ordinary JARs.
- Security: per-request principal and tenant isolation, input validation, bounded processing and no secret leakage; no implicit anonymous deployment.
- Delivery: local only. No modifications to ToastMCP or saas-boilerplate during this bootstrap. Product adoption and package publication are separate steps.

## Outcome 2: Real Spring APIs and an official TypeScript reference — complete

## Outcome 3: Java protocol engine and typed tool contract — complete

- Depends on: Outcomes 1–2.
- Work: implement protocol values, parsing and dispatch under `mcp-2026-core/src/main/java/io/github/enryold/mcp/`. Add an explicit tool registry, execution context, structured result/error contract and JSON Schema validation. Preserve JSON-RPC IDs, unknown permitted metadata and exact field semantics. Reject duplicates in tool registration and invalid schemas before serving requests.
- Work: implement discovery, deterministic authorized listing and invocation independent of servlet/Spring state. Use the pinned schema as a test oracle; generate or hand-model only the needed Java types, with tests preventing schema drift. Cache hints and resultType are part of the wire contract.
- Failure behavior: malformed requests and unsupported versions/methods produce the correct typed protocol failure; expected execution failure produces isError. Unexpected exceptions expose sanitized diagnostics and a correlation ID only.
- Verify: `./gradlew :mcp-2026-core:test`; run schema fixtures for P01–P06 and P08/P11. Tests must not infer correctness solely from serializing/deserializing the same Java DTOs.

## Outcome 5: Security, isolation, schema and failure parity — complete

- Depends on: Outcome 4.
- Work: add scoped Spring Security integration, resource-server sample with local issuer/JWKS, per-request authorization, tenant-isolation fixtures, origin policy, body/depth limits, execution deadlines and rate-limit integration. Reuse existing host security; never install an anonymous global permitAll chain or disable CSRF globally.
- Work: cover all scenario families in `docs/interop.md`: malformed wire, output schema failures, revoked credentials, concurrent callers, version/capability errors, private cache hints, mutation counts and timeout after side effect. Close all required P01–P12 gaps.
- Failure behavior: a timeout is not rollback; retries cannot be implicit. No cached identity or protected data crosses users/tenants. Remote schema reference resolution is controlled and network fetching is denied by default.
- Validation decision (2026-10-14): use pinned RE2/J 1.8 for schema regexes. The installed JDK regex implementation can retain workers after cancellation; RE2/J gives a bounded linear matcher. Unsupported regex syntax fails registration, and this explicit limit must appear in consumer documentation and tests.
- Verify: `./gradlew check`; `npm --prefix interop run e2e`; `npm --prefix interop run sdk:interop`. Independently inspect security cases and failure artifacts before claiming parity.

## Separate future work: product adoption and optional capabilities

- `saas-boilerplate`: add the starter and a representative product tool only after the consumer gate. Follow its AGENTS.md and update its Capability Catalog; Flow Core changes require an actual lifecycle need. No protocol dispatcher or product policy goes into those pure libraries.
- ToastMCP: wrap Ghost service operations with the registration API and preserve paywall, per-member credentials, plan enforcement and accounting. Decide old-client migration separately and prove access-control regressions before switching endpoints.
- Resources/prompts/completions, progress/SSE, subscriptions and MRTR each require their own public API, normative requirements and differential/conformance cases. Full server conformance is a later milestone unless the user expands the first-release scope.
- GitHub creation, commits/pushes, package publication and deployments are not part of the authorized bootstrap.
